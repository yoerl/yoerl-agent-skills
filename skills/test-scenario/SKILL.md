# Test Scenario Mapping

사용자가 **기능·업무 흐름**에 대한 시나리오 테스트 맵·TC 구조를 요청하면 이 스킬만 따른다.  
흐름 이름은 자연어로 주어진다 (예: `식품 장바구니`, `회원 가입`, `챌린지 참여`).

**목표:** 흐름을 코드·문서 기준으로 `TS-*` 단위로 쪼갠 뒤, **`TS-*`마다 시나리오 문서 1개**를 만든다. 각 파일은 `TS → TC` 트리와 케이스 표만 담고, 상세 시퀀스 다이어그램은 쓰지 않는다. 실행·판정·결함 확정 없음(문서만).

**선행:** 상세 TC(10개 항목)를 먼저 만들 필요 없다.

**후행:** 케이스 표의 `TC-*`는 `test-case` 스킬로 10개 항목 상세 TC로 펼친다.

## 핵심 규칙

| 규칙 | 내용 |
|------|------|
| **TS당 1파일** | 한 마크다운 파일에 `TS-*` **1개만.** 여러 `TS-*`를 한 파일에 넣지 않는다. |
| **트리 1:N** | 파일 안 트리는 `TS-*` 1개 아래 `TC-*`만. **하위 `TS-*` 금지.** |
| **트리 ↔ 표 일치** | 트리의 `TC-*` 개수·ID·순서 = 케이스 표 행과 같다. |
| `[확인 필요]` | 코드·기획·스펙으로 확정 못 한 항목은 문구 끝 또는 셀에 표시. 추측으로 빼지 않는다. |
| 결함 미확정 | 실행 전 단계이므로 버그·결함을 **확정하지 않는다.** 의심은 `먼저 볼 케이스` 또는 `[확인 필요]`로만 남긴다. |
| 판정 비움 | 케이스 표 `판정` 칸은 **비운다.** 에이전트가 채우지 않는다. |
| 테스트 실행 안 함 | UI 클릭·API 호출·E2E·단위 테스트 **실행 금지.** 문서 작성만 한다. |
| agent-safety | 제품 코드·설정 값을 바꾸지 않는다. 문서만 쓴다. |
| 양식 SSOT | 골격·절차는 [references/templates/scenario-output.md](references/templates/scenario-output.md). |

## 파일명·접미사

| 항목 | 규칙 |
|------|------|
| 경로 | `docs/test-case/` (플랫. `{타임스탬프}/{도메인}/` 트리에 넣지 않음) |
| 기본 | `{YYYYMMDD_HHMMSS}_{TS_SLUG}_SCENARIO.md` |
| 허용 | `{YYYYMMDD_HHMMSS}_{TS_SLUG}_TESTCASE.md` — 레거시 스타일. **시나리오 단계** 산출에만 쓰고, 상세 TC가 만드는 계층 `…/*_TESTCASE.md`와 경로가 다름(플랫 vs 디렉터리). |
| 타임스탬프 | KST, 배치 작성 시 동일 타임스탬프를 여러 TS 파일에 재사용 가능 |
| `TS_SLUG` | `TS-FOOD-CART-001` → `FOOD_CART` 등 도메인·기능 식별용 `UPPER_SNAKE_CASE` (순번 제외 권장) |

## ID 규칙

- **시나리오:** `TS-{도메인}-{행위}-{순번}` (파일 1개 = `TS-*` 1개)
- **케이스:** `TC-{도메인}-{행위}-{순번}` — 트리·케이스 표에만 적고 상세 10개 항목 본문은 작성하지 않는다
- **중복 방지:** 작성 전 `docs/test-case/`에서 `TS-`·`TC-` grep

## 플랫폼별 힌트 (짧게)

| 플랫폼 | 분해·점검 시 볼 것 |
|--------|-------------------|
| **웹 (Next 등)** | 라우트·권한·토스트/모달·빈·로딩·실패 UI |
| **백엔드 (Spring 등)** | API·RBAC·상태 전이·외부 연동 경계 |
| **모바일 (Flutter 등)** | 화면 스택·딥링크·ViewModel 상태 분기 |

코드·문서가 여러 위치에 나뉘면 프로젝트 문서·소스를 먼저 본다.

## 실행 순서

### 1. 범위·TS 분해

- 흐름을 한 문장으로 정의한다 (시작 → 성공 종료).
- 포함·제외 화면·API·권한을 bullet로 보여 준다.
- 이번 요청에서 쓸 **`TS-*` 목록**을 만든다. TS마다 **별도 파일** 1개가 생긴다.
- 범위가 크면 이번 세션에 쓸 TS만 선택하고, 나머지는 `이번 범위에서 뺀 것`에 남긴다.

### 2. TS마다 TC 분해 (1:N)

- 각 `TS-*`에 대해 `TC-*`를 쪼갠다 (해피·분기·경계·오류). **하위 TS는 만들지 않는다.**
- 트리 초안과 케이스 표 행을 **동시에** 맞춘다.
- 코드 근거(파일·줄)와 `기준 커밋`을 적는다.

### 3. (선택) 관점 점검

파일마다 `## (선택) 관점 점검` 표를 채울 수 있다. 해당 없으면 생략.

### 4. TS당 파일 1개 작성

- 골격: [references/templates/scenario-output.md](references/templates/scenario-output.md)
- 저장: 위 **파일명·접미사** 규칙
- 필수 절: 기준 커밋·근거, (링크) 앞·이어지는 시나리오, 실행 전 준비, 구조(트리), 먼저 볼 케이스(해당 시), 케이스 표, 근거 줄, 이번 범위에서 뺀 것, 기존 문서와의 관계
- 연속 TS는 상호 링크: `앞 시나리오` / `이어지는 시나리오`
- 상세 TC 양식: `test-case` 스킬 `references/template-detailed.md`

### 5. 자체 점검 (파일마다)

- [ ] 이 파일의 `TS-*` **1개만** (제목·트리 루트 1개)
- [ ] 트리 `TC-*` = 케이스 표 `TC-*` (개수·ID·순서)
- [ ] 하위 `TS-*` 없음
- [ ] 케이스 표 `판정` 전부 비움
- [ ] grep ID 중복 없음
- [ ] 테스트 실행·제품 코드 변경 없음
- [ ] `[확인 필요]` 요약이 보고에 포함

## 보고

```
시나리오 테스트 — <흐름>
- 범위: (한 줄)
- 산출: docs/test-case/{timestamp}_{TS_SLUG}_SCENARIO.md × N개 (TS ID 목록)
- TC 개수: (파일별)
- [확인 필요]: M건
- 다음: 상세 TC는 test-case 스킬 (케이스 표 TC ID 기준)
```

## 하지 말 것

- 한 파일에 `TS-*` 2개 이상
- 트리에 `TS-*` 하위에 `TS-*` (TC만 허용)
- 시나리오 단계에서 상세 TC 10개 항목·시퀀스 다이어그램 작성
- Pass/Fail·결함 확정
- `docs/test-case/{타임스탬프}/{도메인}/` 아래에 시나리오 저장
- 기존 시나리오 파일 덮어쓰기 (새 타임스탬프 파일)
