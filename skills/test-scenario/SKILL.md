# Test Scenario Mapping

사용자가 **기능·업무 흐름**에 대한 시나리오 테스트 맵·TC 구조를 요청하면 이 스킬만 따른다.  
흐름 이름은 자연어로 주어진다 (예: `식품 주문`, `회원 가입`, `챌린지 참여`).

**목표:** 한 기능 흐름을 시나리오 단위(`TS-*`)로 분해·점검하고, 실행 전 결함을 확정하지 않은 채 **시나리오 문서 1개**만 만든다. 상세 TC는 `test-case` 스킬로 펼친다.

**선행:** 상세 TC를 먼저 만들 필요 없다. 이미 `*_SCENARIO.md`가 있으면 갱신 대신 새 타임스탬프 파일을 만든다 (기존 문서 본문 `관련 문서`에 링크).

**후행:** 시나리오 문서 끝 `## 상세 TC 대상`에 적힌 범위는 `test-case` 스킬로 펼친다.

## 핵심 규칙

| 규칙 | 내용 |
|------|------|
| `[확인 필요]` | 코드·기획·스펙으로 확정 못 한 항목은 문구 끝 또는 셀에 `[확인 필요]` 표시. 추측으로 빼지 않는다. |
| 결함 미확정 | 실행 전 단계이므로 버그·결함을 **확정하지 않는다.** 의심은 `관점 점검` 또는 `[확인 필요]`로만 남긴다. |
| 판정 비움 | `판정`·`실제 결과`·Pass/Fail 칸은 **비운다.** 에이전트가 채우지 않는다. |
| 테스트 실행 안 함 | UI 클릭·API 호출·E2E·단위 테스트 **실행 금지.** 문서 작성만 한다. |
| agent-safety | 제품 코드·설정 값을 바꾸지 않는다. 문서만 쓴다. |
| 데이터 변경 시 | 사용자가 명시적으로 DB·파일·환경 변경을 요청했을 때만, **대상 환경(로컬/dev/test)** 과 **원복 절차**를 문서 또는 보고에 적고 진행한다. 기본은 데이터 변경 안 함. |

## ID 규칙

- **시나리오:** `TS-{도메인}-{행위}-{순번}` (예: `TS-FOOD-ORDER-001`)
- **상세 TC 예약 ID:** `TC-{도메인}-{행위}-{순번}` — 시나리오 표·트리에 **대응 TC ID**만 적고 본문은 작성하지 않는다.
- **트리 ↔ 표 일치:** 트리에 있는 `TS-*`와 요약 표 행 수·순서·ID가 반드시 같다.
- **중복 방지:** 작성 전 `docs/test-case/`에서 `TS-`·`TC-`를 grep해 이미 쓰인 ID와 겹치지 않게 한다.

## 플랫폼별 힌트 (짧게)

| 플랫폼 | 분해·점검 시 볼 것 |
|--------|-------------------|
| **웹 (Next 등)** | 라우트·권한·동적 세그먼트·리다이렉트·토스트/모달·빈·로딩·실패 UI |
| **백엔드 (Spring 등)** | API 엔드포인트·RBAC·상태 전이·트랜잭션 롤백·외부 연동(결제·알림) 경계 |
| **모바일 (Flutter 등)** | 화면 스택·딥링크·오프라인/세션·권한 다이얼로그·ViewModel 상태 분기 |

코드·문서가 여러 위치에 나뉘면 프로젝트 문서·소스를 먼저 본다.

## 실행 순서 (5단계)

### 1. 범위 확인

- 흐름을 한 문장으로 정의한다 (시작 조건 → 성공 종료 조건).
- 포함·제외 화면·API·권한·연동(결제·알림 등)을 bullet로 적고 사용자에게 보여 준다.
- 범위가 넓으면 한 번에 시나리오 1문서로 묶을지, 흐름을 쪼갤지 확인한다 (쪼개면 `FLOW_SLUG`를 나눈다).

### 2. 시나리오 분해 (TS)

- 해피 패스와 주요 분기(권한·검증 실패·취소·타임아웃 등)를 **시나리오 단위**로 나눈다.
- 각 항목에 `TS-*` ID를 부여하고, 예상 대응 `TC-*` ID를 예약한다.
- 트리(목록 또는 들여쓰기)로 계층을 보여 준다. 하위 시나리오는 부모 `TS-*` 아래에 둔다.

### 3. 관점 점검

아래 관점표를 채운다. 해당 없으면 `해당 없음`. 불확실하면 `[확인 필요]`.

| 관점 | 점검 질문 |
|------|-----------|
| 진입·종료 | 시작 화면/역할·성공·실패 종료가 명확한가 |
| 권한·역할 | 역할별(GUEST/USER/ADMIN 등) 차이가 시나리오에 반영됐는가 |
| 데이터·상태 | 생성·수정·삭제·동시성·멱등에 대한 시나리오가 있는가 |
| 오류·예외 | 네트워크·검증·권한 거절·타임아웃 분기가 있는가 |
| 연동·외부 | 결제·알림·타 시스템 경계가 표시됐는가 |
| 복구·원복 | 실패 후 재시도·롤백·취소 흐름이 있는가 |

### 4. 파일 1개 작성

- 골격: [references/templates/scenario-output.md](references/templates/scenario-output.md)
- 저장: `docs/test-case/{YYYYMMDD_HHMMSS}_{FLOW_SLUG}_SCENARIO.md`
  - 타임스탬프: KST, 문서 작성 직전 `date +%Y%m%d_%H%M%S` 등으로 확인
  - `FLOW_SLUG`: 도메인·흐름 식별용 `UPPER_SNAKE_CASE` (예: `FOOD_ORDER`)
- 트리·시나리오 요약 표·관점 점검·`## 상세 TC 대상`까지 한 파일에 넣는다.
- `## 상세 TC 대상`에 펼칠 `TC-*` 목록과 범위 메모를 적고, 상세 TC는 `test-case` 스킬 (`references/template-detailed.md`)을 참조한다.

### 5. 자체 점검

- [ ] 트리의 `TS-*` 개수·순서 = 시나리오 요약 표와 일치
- [ ] 모든 표의 `판정`·실제 결과 칸이 비어 있음
- [ ] grep으로 ID 중복 없음
- [ ] 테스트 실행·제품 코드 변경을 하지 않음
- [ ] `[확인 필요]` 항목이 보고에 요약됨
- [ ] 산출 경로가 `docs/test-case/`이고 접미사 `_SCENARIO.md`

## 보고

```
시나리오 테스트 — <흐름>
- 범위: (한 줄)
- 산출: docs/test-case/YYYYMMDD_HHMMSS_FLOW_SLUG_SCENARIO.md
- TS 개수: N · [확인 필요] M건
- 다음: 상세 TC는 test-case 스킬 (또는 범위 제한 시 scope 명시)
```

## 하지 말 것

- 시나리오 단계에서 상세 TC 본문(절차·시퀀스 다이어그램 등)을 작성하는 것
- Pass/Fail·결함 확정·버그 티켓 생성 (실행 전 단계)
- `docs/test-case/{타임스탬프}/{도메인}/` 트리 구조에 시나리오를 넣는 것 — 시나리오는 **플랫 `_SCENARIO.md` 1파일**
